# Deep fuzz, 2026-09-28: a returned rental's unit was ETH-backed before its escrow backed it (DF-M-1)

Written 2026-09-28 on branch `invariant-fix` (from `main` at `47c6cf5`). It answers the nightly `contracts-deep` failures of
2026-09-27 and 2026-09-28 (runs 36311295859 and 36412969532, both on `47a9b94`). Nothing was deployed, pushed or signed. The only
chains written to were the dry run's local anvils.

## 1. What failed

`test/floor/FloorModule.invariant.t.sol` → `invariant_noBackingWithoutUnits` (`wrapper.ethBacked() == 0 ⇒ module.backing() == 0`):
`assertion failed: 629242955919139161 != 0` at the deep profile (1,000 runs × 200 calls). The push profile (64 × 64) never
reached it. The shrunk sequence (7 calls on `FloorHandler`, fuzz seed `0xe5f97b93…eb311`):

## 2. Real bug, not a handler artifact

The invariant is right. The two wrappers with rentals (`Wrapper`, `NftWrapper`) say, at `recordReturn`: "the unit this item
backed is backed by its rental's escrowed ETH at the module from now on", and the spec's (M3) counts the escrow back into `B` on the
return. The module did not do that on the return: it waited for a separate, permissionless `settleRental(id)`. Between the two,
the unit is in `ethBacked` and so in `netUnits()` and every backing-per-unit division (`burn`'s `_tierPrices`/`_release`,
`itemArrived`, `advance`, `rentIn`), but its ETH is not in `backing`. Nothing orders the two calls; in the fuzzed sequence the
custodian converts first.

What that window does:

- **A conversion in the window** releases `backing / c` counting a unit with no backing. With that unit the only one (the case
  found) it releases 0 and pays the whole item cost from the revenue pot, then the surplus; the later settle puts one unit's β
  (≈ `F`) into `backing` with **no unit to claim it**. With `c` units, it releases `β·(c−1)/c`, the revenue pot covers the rest,
  and the escrow later over-backs the remaining units.
- **A burn in the window** pays `min(floor − spread, backing / c)` with `c` counting the unbacked unit: burners are paid short when
  `c` is small enough that `β·(c−1)/c` falls under the burn price (a few tens of units at a 1–3 % spread). The shortfall stays and
  goes to later holders.
- **A rental intake or an advance** in the window takes the diluted β the same way.

**Who can recover the stranded ETH, can anyone extract it.** No one can take it: burns never pay above the floor less the spread,
and `skim` never touches `backing`. The next mint's units inherit it as extra backing per unit; conversions then release it to
the revenue pot, which `skim` sends to the platform above `revenueTarget`. If no unit is ever minted again, it stays locked.
The canister and monitor only read `backing`/`escrowBalance()`/`netUnits()`; their numbers were consistent with the contract's
books (solvency and ETH conservation held throughout: `invariant_theModuleIsSolvent`, `invariant_ethIsConserved` pass on the
failing sequence), but the backing per unit they read was wrong in the window.

## 3. Severity: Medium (latent; no launch exposure)

On the audit's scale, a bounded loss that needs a condition: at most one unit's β per returned rental moves from the revenue pot
(or from burners in the window) to later holders, or is stranded; nobody profits; no custody or unbacked mint. It needs rentals ON
and a conversion, burn, rental or advance between the custodian's `recordReturn` and someone's `settleRental`.

**Rentals are OFF in Phase 1 on both sides.** The frog side's `rentIn` is custodian-only and needs a `rentalRoot` the keeper never
posts, and the canister has no rental or return path (`2026-09-26/B-floor.md` §"Rentals"); the Ethereum-NFT side's
`EthNftWrapper` has no rentals at all (`admitRental`/`returnRental` revert `NoRentals`, A-contracts). So nothing at launch can reach
it. It would have become live the day rentals are switched on.

## 4. The fix: the return closes the rental in the same transaction

`recordReturn` is the call that makes the unit ETH-backed, so it now also makes the escrow its backing:

- `IFloorWrapped.sol`: a new `IFloorRentals { rentalReturned(uint256 itemId) }`.
- `FloorModule.rentalReturned(itemId)` — only the wrapper (`NotWrapper`), `nonReentrant`: finds the item's rental
  (`_rentalOfItem`, set in `rentIn`), requires `Leaving` (the wrapper's `Ready → Returned` implies it), and does exactly what
  `settleRental`'s "returned" branch did: `leavingRentals−−`, `Closed`, `rentalEscrow −= escrow`, `backing += escrow`,
  `RentalSettled(id, false, 0, 0)`.
- `settleRental` keeps only the "taken" branch; a returned rental is already closed, so it reverts `NothingToSettle`.
- `Wrapper.recordReturn` and `NftWrapper.recordReturn` call `IFloorRentals(floorModule).rentalReturned(itemId)` last, after their
  own effects. The custodian's call and its signature are unchanged. `EthNftWrapper` has no rentals and is unchanged.

The frog side's rental behavior is otherwise the same: intake, the draw, `endRental`, the taken path, `payDebt`, `claim` and the
escrow amounts are untouched; only the moment the escrow returns to `backing` moved, from a separate call to the return itself.
The window no longer exists, so no ordering of calls can reach the states above.

Sizes (`forge build --sizes`, runtime): `FloorModule` 30,224 → 30,417 B, `Wrapper` 17,831 → 18,752 B, `NftWrapper` 13,021 →
13,942 B; all under 4663's 96 KB limit (`FloorModule` was already above EIP-170's 24 KB before this change).

Off-chain: no service, keeper or canister code calls `settleRental` or `recordReturn` (rentals are OFF); the canister's selectors
are unchanged. `docs/v5/floor-module.md` §9.6 (and its `web-rook` copy) now says the return closes the module's rental.

## 5. The invariant and the handler

The invariant is kept as it was and extended: `invariant_noBackingWithoutUnits` also asserts that no returned rental is ever
found still open (`FloorHandler.returnedUnsettled`, set if `settle` ever sees a `Returned` item whose rental is not `Closed`).
The handler's `settle` now settles only taken rentals, the one case left.

## 7. Confirmation review needed

Yes. This changes `FloorModule`, `Wrapper` and `NftWrapper` after review round 8. The change is small (one new wrapper-only
function, one mapping, one branch removed, one external call at the end of `recordReturn`) and sits on a path that is OFF in
Phase 1, but by this review's rule every contract change is confirmed before launch. Points for the reviewer: the new
wrapper → module call (the first in that direction; the module is `nonReentrant` and makes no external call in it), that a
`recordReturn` can never revert for a legitimate return (`Ready` in the wrapper ⇔ `Leaving` in the module), and that re-renting
an item id points `_rentalOfItem` at the new rental without harm (a returned rental is closed by then; a taken one is settled by
its rental id, never through the mapping).
